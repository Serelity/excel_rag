# 项目调研方法

本文件定义资料如何收集、核验、比较和转化为项目决策。它不预设投诉字段、模型、提示词或指标阈值。

## 1. 从问题开始

每个主题先写清业务目标、两个至五个研究问题、已有假设和暂缓决策。把“想采用什么工具”改写为“什么能力需要证据”。本项目当前主题是历史案例检索输入的结构化，信息抽取准确性与最终检索有用性需要分别验证。

此前讨论的“5 个核心字段、3 个补充字段”属于候选草案。字段名称、定义、拆分方式和模型选择均须接受本轮调研及后续数据核对，不作为筛选文献的前提。

## 2. 来源与检索

| 来源 | 可支持的判断 | 不能直接支持的判断 |
| --- | --- | --- |
| 权威期刊综述与研究 | 任务定义、方法谱系、已报告的实验及局限 | 本项目的最佳字段或最佳模型 |
| 相关同行评审会议论文 | 特定模型、数据集、评价方法 | 跨语言和跨业务的无条件泛化 |
| 原始标注规范 | 概念边界、角色定义、正反例和裁决方法 | 照搬后即适合政务投诉 |
| 官方仓库、源码、测试、发布说明 | 核对版本下的实现能力、许可和使用前提 | 企业生产成熟性、本项目准确率 |
| 官方应用案例 | 某应用的公开实现描述 | 可独立复现的效果或本项目收益 |
| 预印本、博客、聚合索引 | 新方向和线索 | 与期刊、正式评测同等强度的结论 |

学术检索采用互补关键词：信息抽取、实体识别、关系抽取、事件与论元、标注一致性、事实性、时间表达、中文投诉与公共服务。计算机领域的会议论文作为补充，并明确标识为会议；不将其写成期刊。不宣称未核验的期刊分区、CCF 等级、引用量或模型排名。

记录实际使用的数据库、完整查询、日期、过滤方式、命中情况、纳入理由与排除理由。定向检索或人工滚雪球不包装成穷尽性系统综述；只有实际完成对应流程后才报告 PRISMA 覆盖。

## 3. 每条来源怎样核验

论文至少核对标题、作者、年份、正式来源、DOI/官方页面；保留预印本与正式版本的关系。年份冲突记录 online-first 与卷期时间。论文存在与“读到了什么”分开记录：

- **元数据**：确认论文存在，不据此归纳方法细节。
- **摘要**：仅支持摘要直接说明的范围。
- **正文片段**：注明章节、页面或段落位置，结论限制在已读部分。
- **完整正文**：只有实际阅读全文才能使用此标签。

开源项目至少核对实际 owner、默认分支、固定 commit、许可、归档状态及相关文档或代码。项目更名、重定向、模型权重许可与软件许可分开记录。星数只是关注度；不能替代测试、维护、部署资料和目标任务证据。

引用数、仓库状态、发布日期、模型和代码能力都带核验日期。未查询的字段填空并说明原因，不用零代替未知。网页打不开、限流、无开放正文，均记录实际情况，不编造缺失内容。

## 4. 从证据形成判断

每项结论区分三层：

1. **来源陈述**：论文/代码具体说明或实现了什么，并给出定位。
2. **项目解释**：这可能对我们的任务意味着什么，明确属于分析。
3. **待验证假设**：还需要什么本地样例、人工判断或实验才能决定。

同时搜索反例、失败模式、领域迁移和边界不清的情况。不要只找支持已有字段草案或既有 Qwen3 实现的材料。关键区别需单独检查：实体类型与事件角色、逐字证据与语义正确、JSON 合法与事实正确、抽取质量与检索效果、工具能力与业务成熟性。

## 5. 进入设计之前需要沉淀什么

每个候选字段最终应有“定义、包含/排除范围、所属对象、时间范围、允许的变换、缺失/冲突处理、正反例、评价方法”。这些项目是后续研究和讨论清单，本文件不代填最终取值。

方法比较围绕同一组需求开展：中文支持依据、标注需求、实体/关系/事件能力、长文本与多事项处理、证据绑定、结构约束、可拒答性、推理成本、权重与许可、本地部署前提。适合某种字段的工具可能不适合其他字段；是否使用混合流程同样需要实验。

若开展小样本验证，应分开观察字段值、边界、角色归属、事项关联、漏提、无依据新增以及下游检索。开发用样例与独立评测样例分别标识；人工分歧先分析规则问题，不能自动归因于模型。指标和阈值在对应实验方案中确定，调研本身不产生准确率。

## 6. 保存与维护

- 每个主题使用独立文件夹，首页列出问题、材料、结论状态和下一步。
- 机器可读来源、检索日志和 BibTeX 与报告同目录保存。
- 来源原始响应和临时全文仅置于忽略的 `.cache/`；提交目录保留元数据、短证据定位和自行撰写的分析。
- 真实投诉、地址、标注和凭据继续保存在现有私有数据目录，不进入调研报告或公开检索词。
- 修改结论时记录新增证据及版本；已核验来源与未核验线索分别保存。
- 文献元数据校验、重复检查与 Markdown 链接检查是资料一致性检查，不等于科学结论通过验证。

本轮资料整理使用 AI 辅助检索与综合，来源核验范围与未完成事项在各主题报告中公开说明。

## 7. 补充成功实践时怎样研究

2026-10-08 补充：工具功能和一般方法不足以说明一个业务系统怎样做成。实践调研以完整应用为单位，至少记录问题起点、输入和输出、业务流程、字段/表示的用途、方法与数据、人的作用、结果、失败或改进原因、迁移条件。

优先寻找部署方/建设方原始材料、正式生产研究和可核对的开源实现。政府报道可以证明公开上线流程，客户案例可以说明供应商与客户报告的做法；有数据和对照的论文用于进一步检查效果。同行评审身份与随机试验性质分别核对，不能以出版级别代替研究设计。

每个关键数字记录指标对象、分母、基线、相对变化或百分点、时期以及正文位置。指标卡与正文不一致时保留差异，不选择较好数字代替核对。问题数量、会话数量、工作人员数量和训练候选数量分开；系统办理指标不自动归因于其中一个模型。

同一产品的多个版本作为迭代经验，同一新闻的多站转载保留报道链，不重复计算独立成功。固定版本源码只能证明其实现机制，除非客户披露部署配置，否则不能据此还原客户的模型、权重和软件版本。

实践对照同时保留积极经验和具体失败原因。项目建议应写出使用条件，说明哪些可直接借鉴为工作方式，哪些需要本地数据比较。生产部署、离线评估、工程验证阶段和能力文档分别标明；局限用来帮助选择，不替代对实施过程的分析。
