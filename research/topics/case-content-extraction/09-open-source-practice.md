# 开源生态中的实施经验：支持入口、信息归属与组合检索

核验日期：2026-10-08。重点阅读两项应用的实施过程，并核对 Rasa、Haystack 的具体公开实现。应用成效与开源功能分别列证据，便于实际借鉴。

## C10｜JetBrains：把信息收集和知识查询接成服务流程

**场景与来源。** Rasa 官方客户案例《JetBrains Centralizes Developer Support at Scale With Rasa》，页面未标发布日期。本轮读取 The Challenge、The Solution、The Results、The Future。是供应商署名的客户实践，引用了客户人员的说明，未提供可复核原始评测数据。[客户案例](https://rasa.com/customers/jetbrains)

### 实际解决了什么问题

JetBrains 的产品支持长期分散在 100 多个联系表单和入口中。用户需要先找对入口，人工还要往返收集问题上下文，常见问题被反复解答。团队要改善的是整个受理过程。

公开流程可整理为：

```text
统一支持入口
  → 理解用户意图和产品范围
  → 检查问题信息是否完整
  → 判断可以解答还是需要升级
  → 查询按 KCS 方法整理的内部知识库
  → 检查回答质量
  → 解答，或携完整上下文转给合适的人工团队
```

案例明确使用 Rasa Studio 设计会话流程，使支持团队负责人能查看流程逻辑；采用自托管部署。已在主要支持入口上线，同时仍在扩大覆盖。不能把“统一入口的目标”理解为已经完全替换全部 100 多个入口。

### 结果与实施经验

| 公开结果 | 口径与证据位置 |
| --- | --- |
| 约 3,000 次会话/月 | The Results；当时已上线入口的规模，页面没有披露统计月份 |
| CSAT 75–80% | The Results；供应商报告的客户满意度，未披露问卷回收率、样本量和计算细则 |
| 具备完整上下文的人工升级流程 | Building the Agent；是已描述的业务能力，没有单独给出路由准确率 |

最有用的三项经验是：

1. **字段来源于下一步的工作。** 产品范围决定查哪个知识域；问题完整性决定是否还要收集上下文；已有背景帮助人工接手。这给字段设计提供了业务依据。
2. **知识内容本身需要整理。** 案例使用 KCS（Knowledge-Centered Service）框架维护内部知识。我们可以借鉴“把可复用经验组织好”的思路；原始投诉描述本身不等于已经验证的处理方案。
3. **把异常路径一起做进去。** 无法解答时携带已有信息转人工，避免用户从头讲述。对于我们的离线 `case_content`，对应做法是保留缺失或歧义，并把证据一起展示给工作人员；不能通过追问补齐的内容不应自动编造。

**迁移到本项目。** 先问“这一项信息会怎样改变查找、排序或人工判断”，再决定是否抽取。问题主题、事发地点角色、对象和当前诉求可以分别研究；不需要照搬该系统的字段名称。这里的 Rasa Studio 与客户系统配置未开源，案例未公开具体模型、提示词或完整字段表。

## C11｜Airbus + Haystack：把不同信息形式保留下来，分别处理再汇合

**场景与来源。** deepset 官方 Airbus 案例，讲述 AI 研究团队对 Flight Crew Operating Manuals 的文本与表格问答系统。本轮读取 Data Annotation and Preparation、The Solution、Results and Outlook 等正文；页面未显示有效发布日期。[客户案例](https://www.deepset.ai/case-studies/airbus)

### 系统如何做成

飞行手册有上千页，关键词检索要求使用者知道手册的准确措辞。研发过程中，团队发现大量关键内容在表格中，仅处理普通文本会漏掉一整类答案。因此：

1. 组织内部活动，由有实际经验的飞行员参与标注训练数据，供通用文本模型微调。
2. 为表格适配能理解行列结构的表格问答模型。
3. 在预处理阶段添加元数据，保留相似措辞背后的情境差异。
4. 对同一个查询运行文本和表格两条流程，再根据结果置信值汇合。

这是对数据结构的具体响应：先识别信息丢失发生在哪里，再补处理模块。

### 做到了什么，经验适用于哪里

团队报告可以在上千页材料中定位表格单元格，并在 **1 秒以内**给出答案。原文同时明确：**尚未完成系统性用户研究**，仅有积极的早期使用反馈。因此本报告将其列为工程验证阶段的经验，未将其列为航空生产部署成效，也不将这个速度当成可比较的延迟基准；原文没有给出硬件、并发、P95 或统一测试集。

对本项目可迁移的经验是：

- **完整原文与辅助信息可以共存。** 本项目可保留投诉正文，同时将地点角色、对象等信息作为附加表示；不用为了结构化而舍弃原文中的细节。这是我们根据案例作出的工程建议，并非 Airbus 对投诉检索做过实验。
- **相似措辞需要上下文区分。** “同一种故障”发生在不同对象、地点或阶段，可能对应不同历史案例。字段的价值可以来自帮助排序，而不只来自生成一份整齐的 JSON。
- **专业人员参与标注有实际作用。** 哪些上下文改变答案，需要业务人员判断；单靠模型生成示范不能替代这一判断。
- **多路结果汇合需要验证。** 该案例按置信值合并结果，但未公开校准细节。我们的词法、向量、地址分数不能直接当作同尺度概率；具体融合继续沿用并检验项目已有检索机制。

### O08｜Rasa：类型、角色、所属组和业务填槽各自显式表达

核验版本 `3.6.21`，commit `d6829b6acc10fd9548798176bb0f9713107c1555`。选择这一明确版本以核对传统 NLU 的机制，不宣称它是当前推荐的新项目版本。

| 机制 | 固定版本的具体依据 | 对投诉内容的启发 |
| --- | --- | --- |
| 实体类型之外标注 `role` | `nlu-training-data.mdx` 的 Entities Roles and Groups：同为城市，区分出发与到达 | 研究同为地址的居住地、事发地、受理地等角色 |
| 用 `group` 表示归属 | 同一节用两份订单说明数量、规格和对象的组合关系 | 多事项中，对象、地点、诉求要归属到正确事项；不照搬固定的订单组标签 |
| 实体到业务槽位显式映射 | `domain.mdx` 的 `from_entity` 同时支持 `entity`、`role`、`group`、意图条件 | 抽到了一个地址，并不意味着它应自动成为事发地址 |
| 对歧义映射设置限制 | 活跃表单的 unique mapping 机制；无角色城市可能匹配两个所需槽位时，在规定情形下忽略该值 | 对有歧义的信息保留未决，避免同一地址盲填多个不同业务角色 |
| 抽取后做业务校验 | `forms.mdx` 的 `validate_<slot_name>`；示例可将无效值置 `None` 并重新询问 | 逐字引用通过之后，仍可检查地址角色、允许值和信息完整性 |

来源：[角色与组](https://github.com/RasaHQ/rasa/blob/d6829b6acc10fd9548798176bb0f9713107c1555/docs/docs/nlu-training-data.mdx#entities-roles-and-groups)、[槽位映射](https://github.com/RasaHQ/rasa/blob/d6829b6acc10fd9548798176bb0f9713107c1555/docs/docs/domain.mdx#slot-mappings)、[表单校验](https://github.com/RasaHQ/rasa/blob/d6829b6acc10fd9548798176bb0f9713107c1555/docs/docs/forms.mdx#validating-form-input)。

其训练文档还要求实体与角色/组组合具有足够例子，并覆盖不同语序，例如同时覆盖先说起点和先说终点的表达。对于投诉，这给出了实用的样例准备办法：同时检查“住在甲地、投诉乙地”与“乙地有问题、来电人住在甲地”，防止仅靠地址出现顺序猜角色。该例为本报告人工构造。

### O09｜Haystack：内容、元数据和候选融合分别处理

核验 commit `6ca8349091c09af89ec0090aa13cb22de1d88bfb`，commit 日期 2026-10-07。选读的三个源码文件明确实现：

- [`Document`](https://github.com/deepset-ai/haystack/blob/6ca8349091c09af89ec0090aa13cb22de1d88bfb/haystack/dataclasses/document.py)：`content`、`meta`、`score`、dense/sparse embedding 分别保存。
- [`MetadataRouter`](https://github.com/deepset-ai/haystack/blob/6ca8349091c09af89ec0090aa13cb22de1d88bfb/haystack/components/routers/metadata_router.py)：按显式元数据规则分流，并保留 `unmatched` 输出。
- [`DocumentJoiner`](https://github.com/deepset-ai/haystack/blob/6ca8349091c09af89ec0090aa13cb22de1d88bfb/haystack/components/joiners/document_joiner.py)：支持去重拼接、加权融合、RRF 和基于分数分布的融合；这些是可选机制，默认并非 RRF。

因此我们可以把“保存什么信息”“怎样召回”“如何融合排序”分别设计和比较。已有工程能表达多路检索，不意味着新增每个字段都会提升结果。无需为了借鉴这种结构，就把现有 BGE 检索代码全部迁移到 Haystack。
