# 投诉原文抽取规范 v1：第一轮开发版

日期：2026-10-08。规范标识：`case-content-extraction-v1`；提示词：`case-content-extraction-v1-p1`。

本版根据用户完成的80条样例复核，以及“以这个为标准开始第一轮抽取规范开发”的指示制定。目标是为**历史案例匹配**保留问题、条件和原文依据，供后续模型试抽及人工验收使用。

**当前完成的是规范和离线校验工具，不是80条新模型抽取。** 事项划分、角色词表和表示生成办法是本轮提出的可执行设计，后续仍需试抽验证。原人工意见及其落实是依据，不把全部设计都称作人工逐字段确认。

## 1. 依据、版本及使用范围

- 采用 [11 人工复核记录](11-human-review-findings.md) 指向的 `human-review-001/*confirmed*` 当前版本；不采用最初B015待确认版本。
- 80条完成样例级复核；13条意见包括10条地点、1条公司主体、1条咨询意图、1条对象/现象分类。B015“公共厕所是对象、淹水及粪便漂浮是现象”已获用户明确确认。
- 246段现有证据是可追溯参考。其存在与偏移正确，不代表246项均有独立字段金标。
- 80条都已暴露于开发。继续沿用该研究的来源/关联组排除记录，不能作为未见留出样本；正式抽样前须使用审核后的排除表重新准备候选。
- 旧 `semantic-extraction-v4` 保留复现。新实现位于 [case_contract](../../../semantic_extraction/case_contract/)，不改变旧客户端、批处理和历史索引的默认行为。

本版只处理 `case_content`。来源ID可以作传输与审计元数据，不能混入模型用户消息。`case_goal`、结构化地址、业务分类、办理结果、知识引用等均不得作为补充输入。原文正文里本来就有的后续答复可以提取，并须标明来源和作用对象。

## 2. R01：原文与证据

原文不去空格、不做NFKC、不替换标点、不展开字面转义换行。`A_raw`必须逐字保留；指纹用原始字符串UTF-8的SHA256，不能混用历史去重用的归一化哈希。

模型输出 `{"text":"原文连续片段","occurrence":null}`。唯一出现用null；重复出现需提供0起始序号或扩大引文到唯一。程序按Python Unicode字符计算半开区间`[start,end)`，验证`case_content[start:end] == text`。JavaScript展示若使用UTF-16下标，必须另做坐标转换，不能直接套用含表情文本的偏移。

同一片段可以支持多个字段；同一字段可以列出多段证据，但不能将不相邻文字伪装成一段原文。证据需包括否定、疑似、是否等作用域，必要时将限定单列为该字段的第二段证据。选中某个重复位置仅说明引用落在哪里，不能证明该片段属于正确事项。

**程序拒收**无依据的改写、越界序号、未消歧的重复引文及截断JSON；不静默丢掉错误的可选字段，不用别的句子自动替换失败引文。语义归一化只限字段/角色标签；本轮不产出自由改写摘要、同义词扩展、自动补全地址或时间。

## 3. R02：先分流

| route | 判断条件 | 输出与用途 |
| --- | --- | --- |
| substantive | 可辨认业务主题，无明确后续流程 | 有issues，可准备业务案例查询 |
| substantive_with_followup | 可辨认业务主题，同时有后续处置或热线流程 | 有issues；原问题及其后续状态保留，热线流程另列procedure |
| procedure_only | 只有催办、撤单、补录、告知等，原问题未披露 | issues为空，只生成流程表示，不能猜原问题 |
| insufficient_content | 既无主题又无可辨认流程 | issues、procedure均为空；写insufficient_content标记，不生成B查询 |

“咨询无房证明”虽然宽泛，仍是可辨认主题，保留主题并记录重要缺失。“办理完毕”不能单凭这句话推断原投诉已经解决。“联系某机构电话打不通”本身可以是服务问题，不必虚构来电人最初打算咨询的主题。

## 4. R03：怎样组成事项

一个事项围绕一个可辨认的问题目标，携带其对象、背景、条件、影响及诉求。每个事项用一个`topic`原句作为锚点，其他字段按原文实际出现组织。

1. 现象—影响—目标动作一般一项：厕所淹水、无法进入、要求恢复使用。
2. 同一目标的前置障碍和办理环节一般先同组：平台缺少就诊记录，因而咨询报销核实。
3. 同一交易的商品缺陷、沟通及售后经过，不按动词数量拆分。
4. 主体相同但目标可区分时可以拆分：用工安排、社保缴存、欠薪。明确的不同对象问题也可分项。
5. 多个费用名称但关系不明，暂保留一组并标`uncertain_grouping`；不把并列名词直接当确定独立事项。
6. 共享主体和地点仅在原文明示适用于各项时复用；不能把全文地点广播给所有事项。

不沿用旧版“最多3项”的内容截断。模型输出预算不足应记为失败重试或人工处理，不能截成3项后报告成功。v1不建立推断性因果图，字段在事项内的共属也不自动代表因果。多个事项的关系难以判断时记录待复核说明。

## 5. R04—R07：字段边界与角色

字段存于`issues[].facts[]`，仅创建原文支持的字段。每条fact都有全文唯一的`F1…`标识、类型、角色、证据、陈述方式、时序、来源及适用时间。角色是标签，不是新增业务事实。完整枚举见 [JSON Schema](../../specs/case-content-extraction-v1/response.schema.json)。

| kind | 提取内容 | 关键边界 |
| --- | --- | --- |
| topic | 可辨认的问题或咨询主题 | 每事项恰好一项；不要求有故障，不用“未知问题”占位 |
| intent | 咨询、投诉、举报、服务请求、建议等言语目的 | 需依据表达；没有明确依据就不建，不能一律标投诉 |
| actor | 雇主、商家、受影响者、被反映主体、服务方、被查询机构、处理方等 | 保留重要组织名；期待回复部门不自动成为被投诉方 |
| object | 设施、商品、服务、账户、证明、权益、交易等对象 | “公共厕所”是对象，“厕所淹水”是现象；筷子发霉不扩大为食品发霉 |
| problem | 异常现象、行为、障碍或争议 | 可带否定或待核实；咨询无需强造problem |
| request | 希望动作、希望状态、所问信息 | 请求执行与已经执行分开；intent说明说话目的，request说明具体要什么 |
| impact | 已述影响、风险、未实际发生的后果 | “无法进入”是影响，“避免事故”不是事故已经发生 |
| place | 明示的业务地点及其角色 | 事发、居住、登记/户籍、参保、就医、交易、起点、终点、适用地域、地标、机构所在地分开 |
| condition | 身份、资格相关条件、金额、数量、前提等 | 保留单位、范围及近似限定；不推断资格成立 |
| time | 事项/行动时间、期间、频率、相对时间 | 保留表达及所指，不能自动补年月或用当前日期锚定 |
| status | 原问题、工单或措施状态 | issue_state在issues；ticket_state在procedure；action_state按行动对象归属 |

**R05 地点保留。** 原文明示且能区分案例的完整地点，默认提取并进入证据表示，包括已有行政层级、道路与定位参照。一个连续地址链可保留为一条place，多个语义地点分别标角色；不查外部地图补层级。某地址和问题的关系不明时保留原句、role=`unspecified`及`ambiguous_role`。

**R06 主体保留。** 公司名称及其雇主/交易方等角色应保留；学校、停车场等地标不自动成为责任主体。姓名、电话、身份证、工号和工单号不作为常规语义字段；正文原件另存追溯。提取重要机构、商家时保留原名，不能为追求短句改成泛称。

80条旧表达并非逐字符模板。例如某条旧简短表达没有带地址，不意味着本版禁止补充原文有依据的地址。本版把10条地点反馈归纳为默认保留规则；旧样例快照不被覆盖，新输出要另行验收。地址保留与是否启用地址硬过滤是不同决定，v1不自动设置检索过滤。

**R07 意图与现象。** “咨询孩子医保是否参保成功”应保留咨询、孩子、医保、是否成功，状态为待核实；不能变成参保失败。“希望安装”不能提取为已经安装；“险些撞上”不能写成已撞上；“树木遮挡路灯”不能改为灯泡故障。

## 6. R08—R10：陈述方式、时序、缺失与冲突

| modality | 含义 |
| --- | --- |
| asserted | 原文有人这样陈述；不表示外部核验、法律认定或事实真实 |
| possible | 疑似、可能、怀疑 |
| negated | 明确否定；证据必须保留被否定的内容及限定 |
| hypothetical | 假设或计划中的情形 |
| unresolved | 是否、待核实等未定状态 |
| not_applicable | 不形成真假命题的名称、主题、意图或希望动作 |

言语意图与事实性分别保存。例如咨询已发生故障可以同时包含consultation意图和asserted现象；不能把整条咨询所有事实都标成尚未发生。

`attribution`引用原文明示的来源，如居民、社区或系统记录；没说明则null。它不等于对该来源的真实性背书。`phase`为current/background/followup/unspecified；`time_context`只绑定原文明示且适用的时间，不能仅凭最近的时间字符串自动关联。

**R09 状态不串用。** 工单办结是流程状态；现场处理是措施状态；噪声仍持续是原问题状态。已解决历史问题仍有案例检索价值，应保留有用的问题和状态，不一律删掉。原主题缺失时，“仍在处理”只能保留为被催办流程状态，不能推定底层问题的类别、严重性或是否解决。

**R10 缺失不填空。** 没有某字段就不建fact，可空属性用null；不用“未知公司”“未知地址”等虚构引文。缺失影响理解时用missing_context说明，不能补业务原因、资格条件、法律结论或办理环节。

冲突双方分别保留facts及其来源/时序，再用`conflicting_claims`引用至少两项。若可能是后来发生变化，说明待核对，不自动判其中一方错误。指代不清标ambiguous_reference；角色不清标ambiguous_role；事项划分不清标uncertain_grouping。不输出没有校准依据的概率或“置信度95%”。

## 7. R11：从抽取到检索表示

本轮提供三种可追溯材料：

- `A_raw`：原始case_content。
- `B_evidence`：程序按字段类型、角色、时序、陈述方式、来源与引文拼接的证据式表示，保留所有已抽取业务地点和主体。
- `C_raw_plus_evidence`：原文加上述证据表示。

**B_evidence不是此前人工修订的简短B表达。** 本版先让字段与表示可以逐项核对；重复证据和限定可能使B比原文更长。后续若做自由摘要、去重或更短表示，须作为单独版本/变量，不隐去地址、主体、否定或来源。不能把两种B混作同一实验条件。

分析备注不作为新增查询事实；查询只带待复核标记类型及范围。流程表示带`scope=procedure`，不足文本为`scope=insufficient`且B为空。程序不自动发起检索、不执行地址过滤，也不把待复核标记当作人工已通过。

## 8. 可执行结构与使用

模型回复顶层为`spec_version / route / issues / procedure / review_flags`。每事项含issue_id和facts；证据偏移由校验程序生成，模型不计算字符下标。Schema禁止额外字段，所有属性均需出现，可空字段显式为null。

| 文件 | 用途 |
| --- | --- |
| [schema.py](../../../semantic_extraction/case_contract/schema.py) | 字段、角色及跨字段一致性约束 |
| [prompt.py](../../../semantic_extraction/case_contract/prompt.py) | R01—R11提示词；仅接受case_content的模型请求 |
| [validation.py](../../../semantic_extraction/case_contract/validation.py) | 严格证据回映、原文指纹、A/B/C证据表示 |
| [cli.py](../../../semantic_extraction/case_contract/cli.py) | 导出规范、准备请求、校验离线模型回复；输出拒绝覆盖 |
| [规范包](../../specs/case-content-extraction-v1/manifest.json) | Schema、提示词、9个人工构造示例及文件哈希 |
| [80条验收准备脚本](../../scripts/prepare_extraction_contract_review.py) | 绑定confirmed复核快照，生成开发输入及待验收矩阵 |

在已安装项目依赖的Python环境、仓库根目录运行：

```powershell
python -m semantic_extraction.case_contract export --output data/contract-export-001
python -m semantic_extraction.case_contract request --input data/input.json --output data/request.json
python -m semantic_extraction.case_contract validate --input data/input.json --response data/model-response.json --output data/validated.json
```

`input.json`严格只有`{"case_content":"原文"}`。request只准备messages与response_format，不选择模型、不访问服务。模型/服务地址/采样参数由后续适配器明确记录。现有v4客户端不能直接当作v1客户端使用；服务对Schema的支持尚需实测。

校验返回的`contract_prompt_version`表示当前规范配套提示词版本，**不证明外部响应实际由该提示词生成**。后续真实运行还须保存实际请求、原始回复、模型标识、参数、时间、重试及失败原因。

## 9. 第一轮开发验收

验收分三层，不相互替代：

1. **机器检查**：输入字段隔离、严格结构、唯一ID、字段/角色组合、分流一致性、引用范围、每段证据逐字回映。任一失败则拒收整条输出，保留失败记录以供修复；当前CLI不会自动推理重试。
2. **逐条语义检查**：与原文和复核意见对照，检查主题分流、事项分组、字段边界、重要地点/主体遗漏、意图/否定/来源、条件/时间/状态、缺失与冲突。校验通过的输出仍记为语义未评估。
3. **后续检索评价**：固定模型、表示版本、样本与检索设置后另做案例相关性标注；不由抽取通过率推导检索提升。

优先回归13条明确修改：10条地点须保留已指出位置及合适角色，B032保留公司主体，B040保留咨询与待核实，B015分开对象/现象/影响/诉求。它们只是必须检查的回归点，不能代替其余67条的语义复核。

严重错误包括：编造事实、颠倒否定/咨询/计划、错接地点或主体、办结等同实质解决、丢失独立事项、擅自裁定冲突。出现这些错误需修改规则或提示词并对相关样例重新检查。统计时分别报告：格式失败数、证据失败数、人工检查条数及分类型错误数；没有逐字段完整人工标注时不计算字段precision/recall。

80条开发包的`model_output=null`、`semantic_review_status=not_run`及各检查项null必须保持真实，不能从原来accept状态自动置为新规范通过。本版规则是开发起点，不是已证实最优的模型、字段集或事项粒度。
